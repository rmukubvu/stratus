### Kinesis Data Streams: fits, with caveats

An ordered, replayable stream sharded by partition key, read by several consumers.

- **Strength:** The peak needs 4 shard(s) in provisioned mode (1,000 records/s and 1 MiB/s each), or on-demand mode. ([kinesis-shard-write-records](https://docs.aws.amazon.com/streams/latest/dev/service-sizes-and-limits.html))
- **Caveat:** 3 consumers reading every record exceed 2 MiB/s of shared reads per shard; use enhanced fan-out or more shards. ([kinesis-shard-read-bytes](https://docs.aws.amazon.com/streams/latest/dev/service-sizes-and-limits.html))
- **Strength:** Keeps records in order per partition key.
- **Strength:** Consumers can re-read from any point within the retention period.
- **Strength:** Each of the 3 consumers reads the whole stream at its own pace.
- **Load proof:** held at 500/s for 20s (0.25 of the peak, quotas scaled alike): 10,002 requests, 491/s on average, 0 throttled, 0 errors, p99 8.88 ms (run `run-1`, account 934880861408). Finding: low: 491 kinesis PutRecord calls a second, PutRecords barely used.

### Amazon MSK (Kafka): fits, with caveats

Managed Kafka brokers: the Kafka API, long retention and very high throughput, with a cluster to run.

- **Caveat:** Nothing here needs Kafka; a managed queue or stream does the job with no cluster to run.
- **Strength:** Keeps records in order per partition key.
- **Strength:** Consumers can re-read from any offset within retention, which can be long or unlimited.
- **Strength:** Each consumer group reads the whole topic independently.
- **Caveat:** Ops overhead 13/15 is above what the team said it can carry (7/15 for "some").

### SQS standard queue: ruled out

A managed queue: each message goes to one consumer, at least once, in no guaranteed order.

- **Ruled out:** Standard queues make a best effort at order but do not guarantee it.
- **Ruled out:** A consumed message is deleted, so it cannot be replayed.
- **Ruled out:** A queue hands each message to one consumer; 3 independent consumers need fan-out (SNS or EventBridge to a queue each) or a stream.
- **Strength:** Standard queues have no documented per-action throughput quota, so 2,000 messages/s needs no capacity planning.

### EventBridge event bus: ruled out

An event router: rules match events by content and send them to targets.

- **Ruled out:** EventBridge does not deliver events in order.
- **Caveat:** Replay works through archives, which re-send past events to rules; consumers cannot re-read from a position of their own.
- **Strength:** One rule can send every event to up to five targets.

### SNS topic fanning out to SQS queues: ruled out

Publish once; every subscribed queue gets a copy, optionally filtered by content.

- **Ruled out:** Standard topics do not keep order. (FIFO topics with FIFO queues do, at FIFO throughput; not modelled here.)
- **Ruled out:** Queues delete what is consumed, so messages cannot be replayed.
- **Strength:** Each of the 3 consumers gets its own queue and its own copy, and can fail without affecting the others.

### SQS FIFO queue: ruled out

A queue that keeps order per message group and deduplicates, with a throughput quota.

- **Ruled out:** A consumed message is deleted, so it cannot be replayed.
- **Ruled out:** A FIFO queue hands each message to one consumer; 3 independent consumers need fan-out (SNS or EventBridge to a queue each) or a stream.
- **Caveat:** 2,000 messages/s is above the 300 unbatched transactions/s quota; batch sends or turn on high-throughput mode. ([sqs-fifo-unbatched-tps](https://docs.aws.amazon.com/general/latest/gr/sqs-service.html))
- **Strength:** Keeps messages in order within each message group.

## Decision

Chosen option: **Kinesis Data Streams**, because consumers replay orders per customer, and order holds per customer.

## Consequences

- Good: The peak needs 4 shard(s) in provisioned mode (1,000 records/s and 1 MiB/s each), or on-demand mode.
- Watch: 3 consumers reading every record exceed 2 MiB/s of shared reads per shard; use enhanced fan-out or more shards.
- Good: Keeps records in order per partition key.
- Good: Consumers can re-read from any point within the retention period.
- Good: Each of the 3 consumers reads the whole stream at its own pace.

Operational overhead of Kinesis Data Streams (7/15):

| Dimension | Score | Why |
| --- | --- | --- |
| Capacity planning | 2/3 | Shard count to size in provisioned mode, or on-demand cost to watch. |
| Patching and upgrades | 0/3 | Fully managed; nothing to patch. |
| Scaling | 2/3 | Resharding, and hot shards from skewed partition keys. |
| Failure modes and on-call | 2/3 | Iterator age, a poison record stalling a shard, checkpointing bugs. |
| Skills needed | 1/3 | Partition keys, checkpoints and consumer libraries. |
